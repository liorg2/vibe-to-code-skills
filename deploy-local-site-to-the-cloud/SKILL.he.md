# פרסמו את האתר

מאת Vibe to Dev (https://www.vibetodev.com/he). המדריך עם קישורים רשמיים: https://www.vibetodev.com/he/guides/deploy-local-site-to-the-cloud
זמן: 30–60 דקות. עלות: חינם לפרויקט אישי.

שמות המוצרים ב־skill הזה (ספקי אירוח, מסדי נתונים, תשלומים, אימייל, מעקב שגיאות וכלי AI) הם דוגמאות בלבד. קודם בדקו במה הפרויקט באמת משתמש, לפי הקוד, קובצי ההגדרות וקובצי החבילות, והתאימו כל שלב למה שקיים בו. אם שלב מזכיר כלי שהפרויקט לא משתמש בו, בצעו את השלב המקביל בכלי שבו כן משתמשים; אם המשתמשים עוד לא בחרו כלי, הציגו את האפשרויות ותנו להם לבחור. ה־skill הזה עובד בכל סוכן פיתוח ב־AI (Claude Code, Cursor, Codex, Copilot ואחרים). אם מוזכרת פקודה, תיקייה או קובץ של כלי מסוים, השתמשו במקבילה של הסוכן שלכם.

## Rules

- בדקו קודם, הסבירו בשפה פשוטה, שלב אחד בכל פעם. אל תעברו לשלב הבא עד שתנאי "Done when" של השלב הנוכחי מתקיים.
- לעולם אל תיצרו משאבים בתשלום, אל תעשו push, אל תפרסו ואל תגישו בלי לבקש אישור. המשתמשים מבצעים בעצמם כל פעולה בחשבון, כל תשלום וכל לחיצה סופית על פרסום.
- כל שלב מסומן:
  - 👤 YOU: רק המשתמשים יכולים לבצע זאת (חשבון, תשלום, אימות זהות או לוח בקרה). הסבירו והמתינו.
  - 🤖 AI: אתם מבצעים זאת בפרויקט, במסגרת הכללים שלמעלה.
  - 🤝 BOTH: אתם מכינים או בודקים; המשתמשים מבצעים את החלק של החשבון או הפרסום.
- בתיאורי השלבים הפנייה היא למשתמשים; בשורות "Task:" הכוונה ב־"אני" או "עליי" היא למשתמשים: דווחו להם.

## Cloud providers

אל תניחו שמשתמשים ב־Vercel. קודם בדקו באילו ספקים הפרויקט באמת משתמש: חפשו `vercel.json`, `netlify.toml`, `wrangler.toml`, `amplify.yml`, `app.yaml`, `firebase.json`, `fly.toml`, `render.yaml`, `railway.json`, `Dockerfile`, `serverless.yml`, קובצי Terraform או Bicep וזרימות CI, וכן כותרות תגובה של האתר החי (`Server`, `X-Vercel-Id`, `CF-Ray`, `X-Amz-*`). אם עדיין לא ברור, שאלו את המשתמשים. אחר כך השתמשו בשמות של אותו ספק מהטבלאות הבאות.

שמות בתפריטים משתנים. אם תפריט חסר, הסבירו מה לחפש והפנו לתיעוד הרשמי של הספק; לעולם אל תמציאו נתיב בתפריט. גם אצל ספק שלא מופיע בטבלה (DigitalOcean, Hetzner, Heroku, או VPS רגיל) יש אותן משימות: חפשו אותן בתיעוד שלו. ב־VPS רגיל, חזרה אחורה, חומת אש ומגבלות הוצאה הן באחריותכם להגדיר.

| ספק | סודות ומשתני סביבה | יומנים | חזרה לגרסה קודמת | התראת תקציב או מגבלת הוצאה | הגבלת קצב או חומת אש |
|---|---|---|---|---|---|
| Vercel | Project → Settings → Environment Variables | Project → Logs | Deployments → an earlier one → Instant Rollback / Promote to Production | Settings → Billing → Spend Management | Project → Firewall |
| Netlify | Site configuration → Environment variables | Logs (deploys and functions) | Deploys → an earlier one → Publish deploy | Team billing → usage notifications | הגבלת קצב בהגדרות האבטחה של האתר (תלוי תוכנית) |
| Cloudflare Pages / Workers | Settings → Variables and Secrets | Workers Logs, Pages deployment logs | Pages: Deployments → Rollback to this deployment | Billing → Notifications | Security → WAF → Rate limiting rules |
| AWS (Amplify, App Runner, ECS, Lambda) | Secrets Manager או SSM Parameter Store (ב־Amplify: Hosting → Environment variables) | CloudWatch Logs | פריסה מחדש של הבנייה, התמונה או הגדרת המשימה הקודמת | AWS Budgets והתראות חיוב | כללי הגבלת קצב ב־AWS WAF |
| Google Cloud (Cloud Run, Firebase Hosting) | Cloud Run: Variables & Secrets, מגובה ב־Secret Manager | Cloud Logging | Cloud Run: העברת תעבורה ל־revision הקודם. Firebase Hosting: Release history → Rollback | Billing → Budgets & alerts | הגבלת קצב ב־Cloud Armor |
| Azure (Static Web Apps, App Service) | Environment variables או הפניות ל־Key Vault | Log stream, Application Insights | App Service: החלפת deployment slots. Static Web Apps: פריסה מחדש של ה־commit הקודם | Cost Management → Budgets | הגבלת קצב ב־Front Door WAF |
| Render, Railway, Fly.io | Render: Environment. Railway: Variables. Fly: `fly secrets` | יומנים בלוח הבקרה, `fly logs` | Render: Events → Rollback. Railway: פריסה מחדש של פריסה קודמת. Fly: פריסה מחדש של הגרסה הקודמת | התראות שימוש וחיוב (משתנה לפי תוכנית) | הציבו את Cloudflare לפני השירות |

מסדי נתונים, לבדיקות גיבוי וגישה:

| ספק | בדיקת שחזור | מי יכול לגשת |
|---|---|---|
| Neon | יצירת ענף מנקודת זמן בעבר | סיסמאות תפקידים, רשימת IP מורשים |
| Supabase | Dashboard → Database → Backups (שחזור לנקודת זמן בתוכניות בתשלום) | אבטחה ברמת שורה (RLS) בכל טבלה |
| AWS RDS / Aurora | שחזור לנקודת זמן כ־instance חדש | קבוצות אבטחה; לא נגיש פומבית |
| Google Cloud SQL | שחזור או שכפול גיבוי ל־instance חדש | רשתות מורשות או IP פרטי |
| Azure Database | שחזור לנקודת זמן כשרת חדש | כללי חומת אש |
| Firebase (Firestore) | גיבוי מתוזמן או שחזור לנקודת זמן למסד נתונים חדש | Security Rules |

בכל ספק, שחזרו תמיד למסד נתונים זמני חדש, לעולם לא על גבי סביבת הייצור.

## איך לדבר

- קצר, ידידותי ומקצועי. משפטים קצרים ומילים פשוטות. בלי מילות מילוי, בלי מחמאות ובלי לחזור על מה שהמשתמשים אמרו הרגע.
- בכל הודעה: מה מצאתם או עשיתם, ואז הדבר האחד שהמשתמשים צריכים לעשות או להחליט. פרטים רק אם ביקשו.
- שאלו רק מה שאי אפשר למצוא בפרויקט בעצמכם. שאלה אחת בכל פעם, עם הניחוש הטוב ביותר שלכם כתשובת ברירת מחדל.
- ענו על מה שנשאלתם, ועצרו.

## Start

עזרו לי לפרוס את הפרויקט בבטחה. קודם תסתכלו במאגר ותגידו לי איזו מסגרת פיתוח, פקודת בנייה, משתני סביבה, מסד נתונים ודרישות אירוח יש בו. אל תחשפו ערכים סודיים, אל תיצרו משאבים בתשלום, אל תעשו push ל־Git ואל תפרסו עדיין. תנו לי תוכנית קצרה ובקשו אישור לפני כל פעולה שנוגעת בשירות חיצוני.

## 1. הוכיחו שהבנייה עובדת במחשב שלכם

🤖 AI

ספק האירוח מריץ בנייה לסביבת ייצור, לא את שרת הפיתוח. אם הבנייה נכשלת אצלכם, היא תיכשל גם אצלו. בקשו מה־AI להריץ את הבנייה האמיתית, להסביר כל שגיאה בשפה פשוטה ולתקן אחת אחת.

Task: הריצו את הבנייה לסביבת ייצור. אם היא נכשלת, מצאו את סיבת השורש הראשונה, תקנו בצורה הכי קטנה שאפשר והריצו שוב. הראו לי את הפקודה הסופית ואת התוצאה.

```
npm run build
```

Done when: פקודת הבנייה לסביבת ייצור מסתיימת ללא שגיאות, והצגתם למשתמשים את הפלט הסופי.

## 2. שמרו מידע סודי מחוץ לקוד

🤝 BOTH

בקשו מה־AI לוודא ש־.env, .env.local וקובצי מפתחות מוחרגים מ־Git ומעולם לא נכללו ב־commit. (אם התיקייה עדיין לא מאגר Git, הריצו קודם git init או בדקו ישירות את .gitignore.) שידווח רק שמות משתנים, אף פעם לא ערכים. מידע סודי נכנס להגדרות של ספק האירוח בשלב 6, לא ל־GitHub. אם מפתח נכלל אי פעם ב־commit וב־push, התייחסו אליו כאל מפתח שנחשף: צרו מפתח חדש אצל הספק ובטלו את הישן. מחיקת הקובץ לא מחזירה את הסוד.

Task: בדקו אם יש במאגר מידע סודי שנכנס בטעות למעקב. אל תדפיסו ערכים סודיים. בדקו כללי החרגה והיסטוריית Git (אם Git כבר אותחל), ורשמו רק את נתיבי הקבצים ושמות המשתנים שעליי לטפל בהם.

```
git status --ignored
git log --all -- .env .env.local
```

Done when: אף קובץ סודי אינו במעקב או בהיסטוריית Git, או שהמשתמשים החליפו אצל הספק כל מפתח שדלף.

## 3. העלו את הקוד ל־GitHub

👤 YOU

צרו מאגר פרטי וריק ב־GitHub, חברו אליו את התיקייה ובצעו push. דלגו על שלוש השורות הראשונות אם התיקייה כבר מאגר Git עם commits בענף בשם main.

```
git init
git add .
git commit -m "First version"
git branch -M main
git remote add origin https://github.com/<you>/<repo>.git
git push -u origin main
```

Done when: הקוד נמצא במאגר מרוחק פרטי והמשתמשים רואים שם את ה־commit האחרון.

## 4. בחרו ספק אירוח

👤 YOU

ל־Next.js ולרוב אתרי React, Vercel הוא הדרך הקצרה ביותר: נרשמים עם חשבון GitHub. תוכנית Hobby החינמית מיועדת לשימוש לא מסחרי, ולעסק צריך תוכנית בתשלום. Netlify ו־Cloudflare Pages עובדים באותה צורה. גם Hostinger ו־DigitalOcean App Platform אפשריים, בעיקר בתשלום. אתר HTML פשוט מתאים לכולם.

Done when: המשתמשים בחרו ספק אירוח והתחברו אליו.

## 5. העבירו את מסד הנתונים מהמחשב שלכם

👤 YOU

אין לאתר מסד נתונים? דלגו. localhost פירושו "המחשב הזה", ולכן האתר החי לא יכול להגיע למסד נתונים שיושב אצלכם על המחשב. לפני הפריסה הראשונה צרו מסד נתונים מאוחסן (למשל Neon ל־Postgres), הריצו מולו את המיגרציות ושמרו את הכתובת שלו להגדרה DATABASE_URL בשלב הבא.

Done when: דלגו אם אין מסד נתונים; אחרת קיים מסד נתונים מאוחסן, המיגרציות רצו מולו, ומחרוזת החיבור שמורה לשלב הבא (לא בצ'אט).

## 6. ייבאו את המאגר והוסיפו הגדרות

🤝 BOTH

ב־Vercel: Add New → Project → בוחרים את המאגר. מסגרת הפיתוח מזוהה לבד. שאלו את ה־AI אילו שמות משתנים נדרשים, אחר כך העתיקו בעצמכם את הערכים ל־Environment Variables (כולל DATABASE_URL מהשלב הקודם) ולחצו Deploy. אף פעם אל תדביקו ערכים סודיים בצ'אט.

Task: עברו על הקוד והכינו רשימת פריסה: שמות משתני הסביבה הנדרשים, איפה כל אחד בשימוש, והאם הוא נחוץ בזמן בנייה או בזמן ריצה. אל תקראו ואל תדפיסו את הערכים שלהם.

Done when: רשמתם את כל שמות משתני הסביבה הנדרשים, והמשתמשים מאשרים שכל אחד הוגדר אצל ספק האירוח.

## 7. פתחו את האתר וקראו את היומנים

🤝 BOTH

תקבלו כתובת כמו your-app.vercel.app. עברו על המסלול המרכזי באתר. אם משהו נכשל, העתיקו ל־AI את שורות היומן הרלוונטיות (אחרי שהסרתם מהן מידע רגיש) ובקשו אבחון לפני שנוגעים בקוד.

Task: אם הבנייה או הריצה נכשלות ואני מדביק/ה יומני פריסה אחרי הסרת מידע רגיש: הסבירו מה סיבת השורש הסבירה, אילו ראיות תומכות בה ומה התיקון הבטוח הקטן ביותר. אם חסר הקשר, שאלו אותי ואל תנחשו.

Done when: המשתמשים פתחו את הכתובת הציבורית והמסלול המרכזי עובד; כל שגיאה אובחנה מתוך יומנים ללא מידע רגיש.

## 8. פרסמו באמצעות push

👤 YOU

מעכשיו כל push ל־main פורס לאתר החי, וכל ענף אחר מקבל כתובת תצוגה מקדימה משלו. אם גרסה שוברת את האתר, חזרו אחורה דרך ספק האירוח (ב־Vercel: Deployments ← פריסה קודמת ← Instant Rollback / Promote to Production) והחזירו את הגרסה התקינה האחרונה בזמן שאתם מתקנים.

Done when: המשתמשים יודעים ש־push לענף main פורס לאתר החי, ויודעים איפה כפתור ה־rollback של ספק האירוח.

## סיימו כל סשן עם דוח מצב (status report)

| # | שלב | מי | סטטוס |
|---|-----|----|-------|

הסטטוס הוא הושלם (Done), בתהליך (In progress), ממתין לכם (Waiting on you) או טרם התחיל (Not started). מתחת לטבלה: השלב הבא ובדיוק מה על המשתמשים לעשות בו, ואז כל מה שחסום ולמה.
